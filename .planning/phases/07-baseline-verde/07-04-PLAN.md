## Regra de transformação (idêntica nos 4 arquivos)

O que **sai** de cada caso afetado:
- o bloco `await waitFor(() => { expect(screen.getByRole('button', { name: 'Configurar' })).not.toBeDisabled(); });`
- a linha `await user.click(screen.getByRole('button', { name: 'Configurar' }));`
- o bloco `await waitFor(() => { expect(screen.getByRole('button', { name: 'Resultados' })).toHaveAttribute('aria-current', 'step'); });`

O que **entra** no lugar:
- se o caso precisa chegar em Resultados: `await runToResultados(user);` (importado de `@/test/flowHelpers`), que já espera 'Analisar dados', clica e espera a região 'Resultados'. A linha `await user.click(screen.getByRole('button', { name: 'Analisar dados' }));` que existia depois do clique em 'Configurar' é absorvida pelo helper — não deixar as duas.
- se o caso **não** chega em Resultados (só precisa da configuração montada para conferir um nudge, um preview ou um `<select>`): `await screen.findByRole('button', { name: 'Analisar dados' });` sozinho — esperar o botão real aparecer **é** a prova de que o dado carregou.
- se o caso reabria a configuração depois de Resultados (soft reset): o segundo `click('Configurar')` simplesmente some. A seção 'Dados e configuração' nunca desmonta no layout scroll, então o `<select>` de papel de coluna já está na tela e o `selectOptions` seguinte funciona direto.

O que **permanece sem tocar**: o `vi.hoisted`/`vi.mock('chart.js')`, o `SessionProvider`, `vi.useFakeTimers({ shouldAdvanceTime: true })`, os `await vi.advanceTimersByTimeAsync(200)` do debounce de parse (ficam antes do helper, nunca dentro), os cliques em 'Usar exemplo'/colagem, e **todas** as asserções de conteúdo de Resultados (`getByText`, `getByTestId`, checagens de PNG, de métricas e de interpretação).

Referência viva de "como deveria ficar": `src/features/tests/t-student/TStudentTest.test.tsx` e `src/features/tests/correlacao/CorrelacaoTest.test.tsx` — os dois **não** estão na lista de quebrados e já clicam direto em 'Analisar dados' sem passar por nav.
