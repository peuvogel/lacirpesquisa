  <action>
    Create `src/shared/hooks/useLeaveWarning.ts` implementing the `<interfaces>` signature. Inside a `useEffect` with `[hasData]` as the dependency array: return early (attaching nothing) when `hasData` is false; otherwise add a `beforeunload` listener that calls `event.preventDefault()` and sets `event.returnValue = ''`, and return a cleanup that removes exactly that listener.

    Two details are load-bearing and must not be "simplified":
    - The `[hasData]` dependency is what re-attaches the listener whenever the value changes, so the handler's closure is always current. An empty dependency array with an `if (hasData)` check inside the handler is the exact stale-closure bug in Pitfall 2 and must not be used.
    - Do not attempt to set custom prompt text. Modern browsers ignore it and show their own generic dialog; the UI-SPEC records this as browser-controlled copy.

    Do not use React Router's `useBlocker` (01-RESEARCH.md § Alternatives Considered): it would block in-app navigation to Mapas/Variáveis, which fights D-19's "Estatística remains usable standalone" and is not what D-18 asked for. Only real page unload should prompt.

    Write `src/shared/hooks/useLeaveWarning.test.ts` using `renderHook` with spies on `window.addEventListener`/`removeEventListener` filtered to the `beforeunload` event: mounting with `hasData: false` attaches nothing; mounting with `true` attaches exactly one listener; rerendering `true → false` removes it; rerendering `false → true` attaches it; unmounting while `true` removes it; and dispatching a real `beforeunload` event while `true` results in a handler that called `preventDefault` and set `returnValue` (assert via a constructed cancelable event and its `defaultPrevented`). Also assert the listener count never exceeds one across several rerenders, which is the leak this hook could plausibly introduce.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| page unload → browser dialog | The app requests the browser's native confirmation before discarding in-memory data |
| clear action → session state | A destructive, irreversible action on the user's working data |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-NAG | Denial of Service | A `beforeunload` prompt firing when nothing is at stake | mitigate | The listener attaches only while `hasData` is true and only while the Estatística route is mounted, both asserted by tests, so the user is never trapped by an unnecessary dialog |
| T-01-LOSS | Repudiation | Silent loss of pasted work on refresh | mitigate | The native prompt is the intended safeguard, and `Limpar dados` requires an explicit confirmation dialog before destroying data, so no single accidental click loses work |
| T-01-STALE | Tampering | Guard reading a stale `hasData` and failing to warn | mitigate | `hasData` is derived (never stored) in `SessionProvider` and the hook re-attaches on every change via its `[hasData]` dependency; tests cover the true→false and false→true transitions |
| T-01-PRIV | Information Disclosure | Cleared data lingering after `clearSession` | accept | Session state is plain in-memory React state with no persistence layer to purge; JavaScript memory reclamation is out of the app's control and there is no storage copy to leave behind |
</threat_model>
