<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pasted/uploaded user data → parser | Fully untrusted text and binary XLSX bytes enter the app here; this is the phase's primary attack surface |
| parser output → React render | Parsed cell values and error strings flow into components in plans 01-06 / 01-08 |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-XSS | Tampering | Parser output rendered downstream | mitigate | Ported parsers return only plain strings/numbers — never HTML. `escapeHtml` is deliberately NOT ported (01-PATTERNS.md § XSS-safe rendering); rendering safety is delegated to JSX text escaping in 01-06/01-08, and the acceptance criteria here forbid any HTML-string construction inside the ported modules |
| T-01-DoS | Denial of Service | `readTabularFileState` / `unzipXlsxEntries` on a malformed or hostile XLSX | mitigate | Task 2 step 4 guarantees the file path resolves to an `{ status: 'error' }` state instead of throwing, so a bad file cannot crash the Estatística route; the zero-dependency reader also removes a third-party parser from the attack surface |
| T-01-PROTO | Tampering | Mapping objects keyed by parsed header names in the normalizer | accept | Keys derive from user-pasted headers into plain data objects with no prototype-sensitive lookups and no privilege boundary in a client-only app; revisit only if the mapping objects ever feed a server |
| T-01-SC | Tampering | npm dependency surface | mitigate | This plan adds zero new packages — the XLSX reader stays hand-rolled per 01-RESEARCH.md § Don't Hand-Roll, which is verified by the "no xlsx dependency" acceptance criterion |
</threat_model>
