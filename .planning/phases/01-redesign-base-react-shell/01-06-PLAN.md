  <action>
    Create `src/shared/data-input/useTabularInput.ts` returning exactly the shape in `<interfaces>`.

    1. `setRawText` stores the raw text immediately (so the textarea stays responsive and controlled) and parses it through `readTabularPasteState(text, legacyStats, options)`. Empty/whitespace-only text resets to `status: 'idle'` rather than producing an error — a cleared textarea is not a failure. Parsing is synchronous today; still transition through `status: 'parsing'` before committing the result so the UI has a state to render (01-UI-SPEC.md § Loading forbids a blank flash), and debounce the parse by roughly 150ms so a large paste does not re-parse per keystroke.

    2. `setFile` calls `readTabularFileState(file, legacyUtils, legacyStats, options)` inside a `try/catch` at this call site. This is the T-01-DoS mitigation for the file path: a corrupt or hostile XLSX must land in `status: 'error'` with the friendly message, because a React error boundary cannot catch a rejection thrown inside an async event handler (01-RESEARCH.md § Security Domain). On catch, produce the UI-SPEC file-read copy: `Não foi possível ler este arquivo. Tente novamente ou cole os dados diretamente.` with the caught reason pushed into `details` (never rendered as raw English by itself).

    3. Map the parser's `{ status: 'error', message, details }` output straight into the hook's `error` field with no reshaping — plan 01-03 already produces exactly the `{ message, details }` contract the UI needs (01-PATTERNS.md § Friendly parse-error shape).

    4. Guard against stale async results: if `setFile` is called twice, only the latest call may commit state (track a request id or an abort flag), otherwise a slow big XLSX can overwrite a newer fast paste.

    5. `reset()` returns to `idle` and clears `rawText`, `error`, and all parsed fields.

    Write `src/shared/data-input/useTabularInput.test.ts` with `renderHook` + `act`, using vitest fake timers for the debounce: pasting the `;`+metadata fixture reaches `status: 'loaded'` with non-empty `headers`/`bodyRows`; pasting a single junk word reaches `status: 'error'` with a non-empty `details` array; clearing the text returns to `idle`; `setFile` with a `File` built from the CSV-ish fixture reaches `loaded`; `setFile` with a `File` whose `arrayBuffer()` rejects reaches `error` with the Portuguese file-read message and does not throw out of the hook; and two overlapping `setFile` calls leave the later result in state.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pasted text / dropped file → React render | The phase's primary untrusted-input boundary: attacker-controlled strings become DOM content here |
| async file read → component state | A slow or hostile file resolves into state after the fact |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-XSS | Tampering | `TabularInputPanel`, `ColumnPreviewTable` rendering parsed cells and error details | mitigate | All user-derived values render as JSX text children; `dangerouslySetInnerHTML` and `escapeHtml` are both forbidden and enforced by a repo-wide absence gate in this task's verify; a dedicated DOM-level test asserts an `<img onerror>` payload renders inert |
| T-01-DoS | Denial of Service | `useTabularInput.setFile` on a malformed/huge XLSX | mitigate | The file call site is wrapped in try/catch and resolves to a friendly `error` state; a stale-result guard prevents a slow parse from clobbering newer state, so the route stays interactive |
| T-01-ERR | Information Disclosure | Raw exception text surfacing in the UI | mitigate | The user-facing message is always the Portuguese UI-SPEC copy; technical reasons appear only inside the collapsed `Ver detalhes` list, never as the primary message, and never as a stack trace |
| T-01-FILE | Tampering | Arbitrary file types dropped on the dropzone | accept | Files are parsed entirely in the browser with a hand-rolled reader and never executed or uploaded; the `accept` attribute is UX guidance and the parser's error state covers everything else |
</threat_model>
